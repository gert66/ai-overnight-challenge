Wat er echt stond

De oorspronkelijke master prompt

De generieke launch prompt was 27 regels lang. Hij werkte goed, maar safety, Git, tests, fallbackgedrag en de Lovable-policy kunnen grotendeels als vaste systeemregels in de orchestrator staan.

Toon de volledige oorspronkelijke prompt
Read the challenge folder and all supplied public/synthetic context. Build the best complete working solution autonomously using the normal orchestrator flow for planning, implementation, testing, review and polish.

Rules:
- Do not request human intervention for non-essential choices.
- Use only public or synthetic data and documentation.
- Do not use patient data, confidential information or internal source code.
- Do not use sudo/root. User-level dependencies are allowed.
- If a dependency or tool is unavailable, choose a safe alternative and continue.
- Build a polished browser application with clear visual output.
- Test the core functionality end-to-end and fix defects where possible.
- Keep a reproducible source tree, test evidence and a short final report.
- Do not modify unrelated repositories, systems or production environments.

Resource strategy:
- Treat Lovable as a scarce premium resource, not as the default implementation environment.
- Do planning, research, architecture, core logic, coding, debugging, testing, code review and most refinement with the normal orchestrator/model stack and local tools first.
- Use Lovable only for high-leverage frontend work where it is likely to materially improve visual quality, interaction design or final polish.
- Before each Lovable call, ask whether the same improvement can be achieved reliably with local code or the normal model/tool stack. If yes, prefer that route.
- Prefer one well-prepared Lovable pass over many small exploratory Lovable iterations. Batch related UI changes into a single clear request when practical.
- Do not spend Lovable credits on backend logic, algorithm design, data processing, tests, documentation or routine bug fixing unless there is a compelling reason.
- After a Lovable pass, continue refinement, debugging and testing outside Lovable whenever possible.
- Never lower the final quality bar merely to save Lovable credits. Spend credits when they are genuinely needed to make the demo polished and presentation-ready.
- Stop using Lovable once the application is visually coherent, polished and demo-ready. Further cosmetic iteration is not a goal by itself.

Success means: a working demo, objective evidence that the core algorithm works, and a clear account of any remaining limitations.
Zelfstandig bruikbare compacte versie

Dit had waarschijnlijk ook gekund

Voer de gekozen challenge volledig autonoom uit. Lees alle meegeleverde context en acceptance criteria, plan het werk in kleine toetsbare stappen, bouw een gepolijste browserdemo, test de kern end-to-end, laat het resultaat onafhankelijk reviewen en repareer waar nodig. Gebruik alleen publieke of synthetische data, raak geen productie of andere repositories aan, kies veilige alternatieven als tools ontbreken en vraag alleen menselijke hulp als een echte beslissing of toestemming onvermijdelijk is. Leg broncode, commits, testbewijs en een kort eindrapport reproduceerbaar vast.
Nog één stap terug

De seed-prompt die de volgende prompt kan laten maken

Ik wil vannacht een stresstest doen van mijn AI-orchestrator met vijf verschillende softwareproblemen: MOSSE object tracking, een 2×2 Rubik solver, een Monte Carlo particle lab, 3D path planning en een maze-chase game. Werk deze ideeën zelf uit tot concrete challenge briefs en acceptance criteria, maak daarna één herbruikbare launch prompt voor alle vijf, en voer ze volgens onze standaard safety-, Git-, test-, review- en recoveryregels autonoom uit. Het eindresultaat moet per challenge een aantoonbaar werkende browserdemo en eindrapport zijn.

Deze versie is realistisch wanneer de orchestrator de standaard policies al kent. Anders moet de compacte launch prompt hierboven de ontbrekende regels expliciet meenemen.

Ultra-kort

Als de hele omgeving al goed is geconfigureerd

Maak van de vijf gekozen ideeën een overnight stresstest voor mijn orchestrator. Genereer zelf challenge briefs, acceptance criteria en één herbruikbare launch prompt. Voer daarna alle vijf autonoom uit volgens onze bestaande safety-, Git-, test-, review- en recoveryregels en lever vijf aantoonbaar werkende browserdemo’s op.
Het interessante punt: de echte menselijke input kan dus veel meer op een gewone doelbeschrijving lijken. De technische details kunnen door de omgeving en door een tussenstap met AI worden gegenereerd.
