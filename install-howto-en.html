Beginner guide

From zero to your first AI build environment

This page assumes you do not yet have a server, a GitHub connection, or experience with SSH. Follow the steps in order. First we get one VM and one coding agent working reliably. Only then do we add automation.

1. Create the three accounts

1GitHub

Go to github.com/signup, create an account and enable two-factor authentication. Then create an empty repository, for example my-ai-builds.

2Hetzner Cloud

Create an account with Hetzner Cloud Console. You will create one small Ubuntu server here.

3AI account

For this guide we use Claude Code on the VM because it is a documented terminal agent. According to Anthropic, Claude Code can authenticate with Claude Pro/Max or through the Anthropic Console. For the human chat layer, you can use ChatGPT or Claude.

2. Create an SSH key on your own computer

SSH is the secure connection between your laptop and the Linux VM.

Windows PowerShell

ssh-keygen -t ed25519 -C "your-email@example.com"

Press Enter to use the default location. The public key is usually located at C:/Users/YOUR_NAME/.ssh/id_ed25519.pub.

type $env:USERPROFILE/.ssh/id_ed25519.pub

macOS / Linux

ssh-keygen -t ed25519 -C "your-email@example.com"
cat ~/.ssh/id_ed25519.pub
Copy only the public key, the file ending in .pub. Never share your private key.

Official GitHub guide to SSH keys.

3. Create the Hetzner VM

1Open the Hetzner Cloud Console and create a project, for example AI-Lab.
2Choose Servers → Add server.
3Choose a location close to you.
4Choose Ubuntu as the image.
5Choose a small instance around 2 vCPU / 4 GB RAM. As a rough estimate, expect about €6 to €7 per month and check the current price before ordering.
6Under SSH key paste the public key from step 2.
7Name the server, for example ai-builder-01 and click Create & Buy Now.

Official Hetzner guide.

4. Make the first SSH connection

Hetzner shows a public IP address. Replace SERVER_IP below with your actual IP.

ssh root@SERVER_IP

The first time, SSH asks whether you trust the fingerprint. Verify that you are connecting to the correct IP and then answer yes.

Create a regular administrator account immediately

adduser aiadmin
usermod -aG sudo aiadmin
mkdir -p /home/aiadmin/.ssh
cp /root/.ssh/authorized_keys /home/aiadmin/.ssh/authorized_keys
chown -R aiadmin:aiadmin /home/aiadmin/.ssh
chmod 700 /home/aiadmin/.ssh
chmod 600 /home/aiadmin/.ssh/authorized_keys

Then test in a new terminal:

ssh aiadmin@SERVER_IP

6. Connect the VM to GitHub

ssh-keygen -t ed25519 -C "ai-builder-01"
cat ~/.ssh/id_ed25519.pub

Copy the public key. On GitHub, go to Settings → SSH and GPG keys → New SSH key and paste it there. Then test:

ssh -T git@github.com

Set your Git identity and clone your repository:

git config --global user.name "Your Name"
git config --global user.email "your-email@example.com"

cd ~/projects
git clone git@github.com:YOUR_GITHUB_NAME/my-ai-builds.git

7A. Optional but very useful: Desktop Commander

Desktop Commander is the tool bridge between ChatGPT and your VM. The orchestrator controls autonomous jobs and Hermes provides read-only advice. Desktop Commander serves a different role: when you ask, it can directly inspect and operate the machine by reading and editing files, browsing directories, starting processes, following logs, and running terminal commands.

Install and connect it

Node 18 or newer is required. Start the Remote Device on the VM:

npx @wonderwhy-er/desktop-commander@latest remote

The first run shows a one-time verification code. Confirm that code in the browser. Then add the Remote MCP server in ChatGPT or another MCP-compatible client:

https://mcp.desktopcommander.app/mcp

After OAuth authorization, the chat can reach the paired VM while the Remote Device is running. On our challenge VM, Desktop Commander Remote runs as a persistent service, so the connection does not depend on keeping an SSH terminal open.

Why this is useful

It removes a lot of manual SSH copy-and-paste work. ChatGPT can, for example, check whether a service is running, edit a configuration file, inspect a log, or check Git status while you remain in the same conversation.

Important: Desktop Commander has execution capabilities on the machine within its configured access boundaries. Treat it like administrator access: restrict allowed directories and commands, keep secrets out of Git, and connect only machines you deliberately prepared for this purpose. Verify pairing codes before authorizing a new device.

Official Remote Desktop Commander guide.

8. Set environment variables and secrets securely

Never put tokens or API keys directly in code or Git.

Project-specific .env file

cd ~/projects/my-ai-builds
nano .env

Example:

APP_ENV=development
MY_SERVICE_TOKEN=paste_a_real_token_here

Keep the file out of Git:

printf "
.env
.env.*
" >> .gitignore
chmod 600 .env

Non-secret shell settings

nano ~/.bashrc
# example:
export AI_PROJECT_ROOT="$HOME/projects"
source ~/.bashrc
For real production secrets, use a secrets manager. For a first private experiment, an uncommitted file with strict permissions is a reasonable starting point.

9. First perform one manual end-to-end test

cd ~/projects/my-ai-builds
mkdir hello-agent && cd hello-agent
npm init -y
printf 'console.log("AI build environment works")
' > index.js
node index.js

Then have the coding agent add one test. Check the result and push a separate branch:

git checkout -b experiment/first-agent-test
git add .
git commit -m "First agent environment test"
git push -u origin experiment/first-agent-test
Only add the orchestrator once VM → agent → test → Git commit → GitHub push works.

10. Then add the orchestrator

Version 1 only needs to do six things:

PhaseFunction
PLANCreate one concrete build step with acceptance criteria.
BUILDStart the coding agent in the correct repository.
TESTRun fixed test commands.
REVIEWHave a separate review run check the result.
COMMITCommit only when the evidence and review are green.
REPEATRepeat until the acceptance criteria are met.

Store state outside the model, for example in state.json, so a restart can resume.

11. Add monitoring and a watchdog

Have active jobs periodically write a heartbeat. A separate watchdog checks whether that heartbeat is still recent and only takes action when a job has demonstrably stalled.

{
  "job_id": "demo-001",
  "phase": "WORKING",
  "heartbeat": "2026-09-17T08:30:00Z"
}

On Linux, use for example systemd for the orchestrator and a timer or cron for periodic checks. Always give retries a maximum.
