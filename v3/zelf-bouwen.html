Wat heb je nodig?

Voor een eerste persoonlijke opzet is dit voldoende.

  • Een GitHub-account (repositories, commits, audit trail)
  • Een kleine Linux cloud-VM, bijvoorbeeld bij Hetzner Cloud (rond 2 vCPU / 4 GB RAM)
  • Een AI-account, bijvoorbeeld ChatGPT of Claude, plus een coding agent op de VM (in deze handleiding: Claude Code)
  • Een SSH-key op je eigen computer
  • Basissoftware op de VM: Git, Python, Node/npm
  • Optioneel: Desktop Commander, voor directe, begrensde VM-toegang via ChatGPT

Wat kost het ongeveer?

De vaste kosten zijn overzichtelijk. Je hebt geen GPU-server of groot cloudplatform nodig. Controleer actuele prijzen bij de provider vóór je bestelt.

De route, stap voor stap

Twaalf stappen, dezelfde volgorde als de originele beginner-handleiding. Elke stap linkt naar het volledige commando-voor-commando recept.

  1. 1

    Maak de drie accounts

    GitHub (voor code en audit trail), Hetzner Cloud (voor de VM) en een AI-account. Voor de coding agent op de VM gebruikt de originele handleiding Claude Code; voor de menselijke chatlaag kun je ChatGPT of Claude gebruiken.

    Volledige uitleg →

  2. 2

    Maak een SSH-key op je eigen computer

    SSH is de veilige verbinding tussen jouw laptop en de Linux-VM. Deel nooit je privésleutel, alleen het publieke .pub-bestand.

    Volledige uitleg →

  3. 3

    Maak de VM

    Een kleine Ubuntu-server met rond 2 vCPU en 4 GB RAM is voldoende, voor ongeveer €6–7 per maand als orde van grootte.

    Volledige uitleg →

  4. 4

    Verbind met de VM en maak een gewone beheerder

    Log de eerste keer in als root, maak daarna een gewone beheerdersaccount aan en gebruik die voor het dagelijkse werk.

    Volledige uitleg →

  5. 5

    Installeer de basissoftware

    Git, Python, en Node/npm (via nvm) zijn de minimale ontwikkelomgeving.

    Volledige uitleg →

  6. 6

    Koppel de VM aan GitHub

    Een eigen SSH-key voor de VM, je Git-identiteit instellen en je eerste repository clonen.

    Volledige uitleg →

  7. 7

    Installeer en activeer de coding agent

    Begin interactief en laat de agent eerst één simpele taak doen. Optioneel: Desktop Commander als gereedschapsbrug, los van de autonome state machine.

    Coding agent → · Desktop Commander (optioneel) →

  8. 8

    Zet environment variables en secrets veilig

    Tokens en API-keys horen nooit rechtstreeks in code of Git. Gebruik een lokaal .env-bestand met strikte rechten, buiten Git.

    Volledige uitleg →

  9. 9

    Doe eerst één handmatige end-to-end test

    Bewijs dat agent, Git en tests werken vóórdat je automatiseert: een kleine test schrijven, laten committen en pushen naar een aparte branch.

    Volledige uitleg →

  10. 10

    Voeg daarna de orchestrator toe

    Een eerste versie hoeft maar zes dingen te kunnen: PLAN (één concrete bouwstap met acceptance criteria), BUILD (de coding agent laten werken), TEST (vaste testcommando's draaien), REVIEW (een aparte, onafhankelijke controle), COMMIT (alleen na groen licht) en REPEAT.

    Volledige uitleg → · De volledige architectuur →

  11. 11

    Voeg monitoring en een watchdog toe

    Laat actieve jobs periodiek een heartbeat schrijven en laat een aparte watchdog ingrijpen als een job aantoonbaar stilvalt. Geef retries altijd een maximum.

    Volledige uitleg →

  12. 12

    Eindcheck, dan je eerste run — en de volgende ochtend beoordelen

    Loop de eindcheckpunten langs (SSH, GitHub, agent, secrets, tests, state, retries, Git, watchdog). Kies daarna een taak die in een paar uur aantoonbaar kan slagen of falen, schrijf vooraf een paar concrete acceptance criteria en laat de orchestrator autonoom bouwen tot de tests groen zijn of een echte menselijke beslissing nodig is. Beoordeel de volgende ochtend het resultaat: werkt de demo, is er testbewijs, en zijn de commits logisch te volgen?

    Volledige eindcheck →

Let op: zet nooit API-keys of tokens rechtstreeks in code of Git. Gebruik een lokaal .env-bestand met strikte rechten en houd het buiten Git.
Een goede eerste proef: “Bouw een browserapp die X doet, schrijf de tests vóór de implementatie, werk op een aparte Git-branch, commit alleen na onafhankelijke review en geef NEEDS_HUMAN terug als een productbeslissing nodig is.”
