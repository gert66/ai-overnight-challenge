How did we do this in one night?

The experiment started after our physics meeting. About twenty minutes of talking things through with ChatGPT about the rules, five challenges, and a live progress page was enough to define the framework. The VM with Hermes and the orchestrator had only been running since Sunday. Hermes provided a separate read-only advisory layer: the orchestrator remained authoritative, while Hermes could analyse job data and return additional AI advice without modifying files or the workflow itself. The system was then instructed to plan, build, test, review, repair, and publish autonomously.

What made this unusual?

The test was not about one model writing a nice code fragment. It was about a chain that keeps working independently for hours and demonstrably checks whether the result is correct.

One human entry point

The assignment and constraints came in natural language. Execution was then split into small, testable batches.

Planner, Worker, Reviewer

The orchestrator kept the roles separate. The planner determined the next step, the worker built it, and the reviewer independently checked it against the acceptance criteria.

Git as memory

Every accepted batch received a commit. This kept development reproducible, visible, and recoverable.

Tests as the gate

Unit tests, type checks, builds, and where possible Playwright end-to-end tests determined whether a step could move to the next phase.

How the AI build environment works

From your question in ChatGPT to code, tests, and a working demonstrator on the VM. The orchestrator controls the whole chain. Hermes sits alongside it as an isolated read-only advisory layer: it can analyse current job and audit data and return advice, while the orchestrator always remains the decision-making and execution layer.

Hermes as a safe extra AI layer

In this setup, Hermes is deliberately separated from the executing orchestrator. The orchestrator exports only allow-listed job and audit data to a separate read-only environment. Hermes can analyse that information and return advice, but it cannot modify files or execute actions. This lets you add extra AI expertise or switch models/providers without giving up control of the workflow.

Practical advantage: the core workflow stays stable and auditable, while different models can be used for planning, coding, review, diagnosis, or a second opinion. Hermes acts here as a safe bridge to that additional advisory layer.

Gemini Flash as an additional model option

Alongside Claude, Gemini Flash can be an interesting fast and relatively low-cost provider for agentic workloads. Google runs Gemini on its own TPU infrastructure and positions the Flash family specifically for efficient coding and agent tasks. That makes Flash useful alongside other models, for example for parallel reviews, lighter batches, or fallback routing, reducing dependence on the usage limits of a single provider.

Note: prices and limits change. Treat Flash as another route in your model mix rather than a fixed cost promise. As of September 2026, Google lists introductory Gemini 3.8 Flash pricing of USD 0.75 per million input tokens and USD 3.75 per million output tokens through December 31, 2026.

What I take away from this

The surprising result was not that a language model can write software. The bigger step was that a fairly small VM with a good orchestrator could organize, check, and recover software development independently for several hours. The human work shifted from writing lines of code to defining the assignment, the boundaries, and the acceptance tests.
