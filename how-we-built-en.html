How did we do this in one night?

The experiment started after our physics meeting. About twenty minutes of talking things through with ChatGPT about the rules, five challenges, and a live progress page was enough to define the framework. The VM with the orchestrator had only been running since Sunday. The system was then instructed to plan, build, test, review, repair, and publish autonomously. The core was the controlled loop around the models: state, evidence, independent review, commits, and recovery were enforced by the orchestrator.

What made this unusual?

The test was not about one model writing a nice code fragment. It was about a chain that keeps working independently for hours and demonstrably checks whether the result is correct.

One human entry point

The assignment and constraints came in natural language. Execution was then split into small, testable batches.

Planner, Worker, Reviewer

The orchestrator kept the roles separate. The planner determined the next step, the worker built it, and the reviewer independently checked it against the acceptance criteria.

Git as memory

Every accepted batch received a commit. This kept development reproducible, visible, and recoverable.

Tests as the gate

Unit tests, type checks, builds, and where possible Playwright end-to-end tests determined whether a step could move to the next phase.

How the AI build environment works

From your question in ChatGPT to code, tests, and a working demonstrator on the VM. The orchestrator controls the whole chain. Brain, Worker, and Reviewer are AI roles inside a deterministic control plane. Hermes sits outside this core loop and is used only optionally as a read-only advisory layer in selected problem cases.

Desktop Commander: a direct tool bridge to the VM

Desktop Commander Remote ran on the same VM alongside the autonomous orchestrator. When explicitly requested, it allowed ChatGPT to inspect and edit files, start or follow processes, read logs, and execute terminal actions directly. This was particularly useful for administration, diagnosis, and quick changes during the challenge.

How the roles differ: the orchestrator controls autonomous jobs. Desktop Commander gives ChatGPT tools to inspect and operate the machine directly. Hermes is an optional read-only advisory layer and is not part of the normal state-machine loop.

Where Hermes actually fits

Hermes sits outside the normal Brain → Worker → Evidence → Reviewer loop. In the current code, Hermes is consulted only as a read-only advisory layer for selected retry or problem situations. Hermes does not control the state machine, execute Git, write code, manage model routing, or decide whether the workflow continues.

Important: the autonomous build loop can technically function without Hermes. Hermes is mainly an additional memory and advisory layer for incidents, knowledge reuse, and later operational agents.

Models: roles and providers are separate

The current implementation is specific: Brain and Reviewer run through Claude. Only the Worker is provider-selectable with auto, Claude, Gemini, or Codex. In auto mode, LOW/NORMAL work can go to Gemini 3.8 Flash; higher complexity and selected escalations go to Claude Sonnet. Git safety, evidence, review, and commits remain with the orchestrator.

So: provider switching is real, but it does not apply to every role. Future flexibility is no longer presented as if it were fully live today.

What I take away from this

The surprising result was not that a language model can write software. The bigger step was that a fairly small VM with a good orchestrator could organize, check, and recover software development independently for several hours. The human work shifted from writing lines of code to defining the assignment, the boundaries, and the acceptance tests.
