I want to build this myself

For anyone who wants to set this up themselves, at home or in the department. You don't need to be an experienced programmer, but you do need to be willing to work with a terminal. You'll need a computer, an account with a

model providerThe model provider is the company that supplies the AI model that does the reasoning and writing.
and some time. This is a condensed route; the full commands are on the existing site.

Steps 1–3: accounts, an SSH key and your first VM

Start with three accounts: GitHub (for code and version control), a cloud provider such as Hetzner (for the VM) and an AI account (for example Claude Code as a coding agent on the VM, and ChatGPT or Claude for the human conversation). On your own computer, create an SSH key, and use it to create a small Ubuntu VM, on the order of 2 vCPU and 4 GB RAM.

Full explanation: creating accounts · Creating an SSH key · Creating the VM · The first connection

Steps 4–5: installing software and connecting GitHub

Install the basic software on the VM: Git, Python, Node/npm and the usual build tools. Then connect the VM to GitHub with its own SSH key, so the VM can later commit and push by itself.

Full explanation: installing software · Connecting GitHub

Step 6: the coding agent and a tool bridge

Install a coding agent on the VM, for example Claude Code, and let it first do one simple task interactively before anything runs autonomously. Optionally, you can also add Desktop Commander: a tool bridge that lets a chat AI, separate from the autonomous orchestrator, directly view and change files, processes and logs on the VM when you explicitly ask for it.

Full explanation: installing the coding agent · Desktop Commander (optional)

Steps 7–9: secrets, a first test and the orchestrator

Never put API keys and tokens directly in code or Git; use a file that isn't committed, with strict permissions. Then do one manual end-to-end test first: VM → agent → test → Git commit → GitHub push. Only once that works reliably should you add the orchestrator. A first version only needs to know six phases: plan, build, test, review, commit and repeat.

Full explanation: setting up secrets · The first manual test · Adding the orchestrator

Steps 10–12: monitoring, watchdog and a final check

Have active jobs write a heartbeat, and set up a separate watchdog that intervenes if a job demonstrably gets stuck, with a maximum number of attempts. Before you let the environment work on its own, run through a final check: does SSH work, can it push to GitHub, do the tests run with a clear result, and is every accepted step a separate Git commit?

Full explanation: monitoring and watchdog · The full final check

Start deliberately small

Don't build everything at once. Start with one VM, one GitHub repository and one AI environment. Only add reviews, retries, multiple model providers and a dashboard once the simple chain already works reliably. Choose a first trial task that can demonstrably succeed or fail within a few hours, and write five to ten concrete acceptance criteria before you start.

Start from the story, not from the technology

The way this experiment came about is itself a method you can reuse: start with an idea in plain language, and let AI work that idea out itself into a

, with a challenge brief, acceptance criteria and an executable assignment. Only then does the orchestrator need to build, test, review and repair it autonomously.

Five ready-made examples

Use these repositories as an example of what comes out of this approach:

  • 01 MOSSE Tracker — tracks a designated object through a video.
  • 02 Rubik 2x2 — solves a 2x2 cube and animates every move in 3D.
  • 03 Electron Dose Lab — physics Monte Carlo research demo with public NIST data.
  • 04 3D Path Planner — finds and shows a safe route through a 3D obstacle world.
  • 05 Maze Chase — an original maze chase game in the browser.
Honest expectations

The value isn't in expensive hardware, but in the orchestrator that reliably ties all the steps together: so start deliberately small and only expand once the basic loop runs reliably. Provider flexibility today concretely exists for the Worker role (Brain, Worker and Reviewer are the three AI roles; see Show me under the hood); Brain and Reviewer run fixed via Claude in this implementation. And not every result suits every purpose: the Electron Dose Lab demo, for example, is a physics research demo based on public NIST data, not a clinical device and not a clinically validated dosing system.
