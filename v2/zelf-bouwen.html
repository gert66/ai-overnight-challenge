Stap 1–3: accounts, SSH-key en je eerste VM

Begin met drie accounts: GitHub (voor code en versiebeheer), een cloud-provider zoals Hetzner (voor de VM) en een AI-account (bijvoorbeeld Claude Code als coding agent op de VM, en ChatGPT of Claude voor het menselijke gesprek). Maak op je eigen computer een SSH-sleutel, en gebruik die om een kleine Ubuntu-VM aan te maken, orde van grootte 2 vCPU en 4 GB RAM.

Volledige uitleg: accounts aanmaken · SSH-key maken · De VM aanmaken · De eerste verbinding

Stap 4–5: software installeren en GitHub koppelen

Installeer op de VM de basissoftware: Git, Python, Node/npm en de gebruikelijke bouwtools. Koppel daarna de VM aan GitHub met een eigen SSH-sleutel, zodat de VM later zelf kan committen en pushen.

Volledige uitleg: software installeren · GitHub koppelen

Stap 6: de coding agent en een gereedschapsbrug

Installeer een coding agent op de VM, bijvoorbeeld Claude Code, en laat die eerst interactief één simpele taak doen voordat er iets autonoom draait. Optioneel kun je daarnaast Desktop Commander toevoegen: een gereedschapsbrug waarmee een chat-AI, los van de autonome orchestrator, rechtstreeks bestanden, processen en logs op de VM kan bekijken en aanpassen wanneer jij daar expliciet om vraagt.

Volledige uitleg: coding agent installeren · Desktop Commander (optioneel)

Stap 7–9: secrets, een eerste test en de orchestrator

Zet API-keys en tokens nooit rechtstreeks in code of Git; gebruik een niet-gecommit bestand met strikte rechten. Doe daarna eerst één handmatige end-to-end-test: VM → agent → test → Git-commit → GitHub-push. Pas als dat betrouwbaar werkt, voeg je de orchestrator toe. Een eerste versie hoeft maar zes fasen te kennen: plannen, bouwen, testen, reviewen, committen en herhalen.

Volledige uitleg: secrets instellen · De eerste handmatige test · De orchestrator toevoegen

Stap 10–12: monitoring, watchdog en eindcheck

Laat actieve jobs een heartbeat wegschrijven en zet een aparte watchdog neer die ingrijpt als een job aantoonbaar vastloopt, met een maximum aantal pogingen. Loop voor je de omgeving alleen laat werken een eindcheck af: werkt SSH, kan er naar GitHub gepusht worden, draaien de tests met een duidelijke uitslag, en is elke geaccepteerde stap een aparte Git-commit?

Volledige uitleg: monitoring en watchdog · De volledige eindcheck

Begin bewust klein

Bouw niet meteen alles tegelijk. Begin met één VM, één GitHub-repository en één AI-omgeving. Voeg pas daarna reviews, retries, meerdere modelaanbieders en een dashboard toe, zodra de eenvoudige keten al betrouwbaar werkt. Kies als eerste proef een taak die in een paar uur aantoonbaar kan slagen of falen, en schrijf vóór de start vijf tot tien concrete acceptance criteria.

Start vanuit het verhaal, niet vanuit de techniek

De manier waarop dit experiment ontstond, kun je zelf hergebruiken als methode: begin met een idee in gewone taal, en laat AI dat idee zelf uitwerken tot een

promptEen prompt is een instructie in gewone taal, geschreven of gesproken, die je aan AI geeft, bijvoorbeeld een opdracht of vraag waar een resultaat uit moet komen.
, met een challenge brief, acceptance criteria en een uitvoerbare opdracht. Pas daarna hoeft de orchestrator het autonoom te bouwen, testen, reviewen en herstellen.

Eerlijke verwachtingen

De waarde zit niet in dure hardware, maar in de orchestrator die alle stappen betrouwbaar aan elkaar knoopt: begin daarom bewust klein en breid pas uit als de basisloop betrouwbaar draait. Provider-flexibiliteit bestaat vandaag concreet voor de Worker-rol (Brain, Worker en Reviewer zijn de drie AI-rollen; zie Kijk onder de motorkap); Brain en Reviewer draaien in deze implementatie vast via Claude. En niet elk resultaat is voor elk doel geschikt: de Electron Dose Lab-demo bijvoorbeeld is een natuurkundig onderzoeksdemo op basis van publieke NIST-data, geen klinisch apparaat en geen klinisch gevalideerd doseersysteem.
